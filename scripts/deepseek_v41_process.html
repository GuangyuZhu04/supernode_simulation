    03 / FOLLOW THE RESOURCE CLOCK

    从算子工作量，到一个可推进的时钟

    右侧可逐条查看本次运行的实际算子。累计时刻由原生阶段 trace 的时长顺序累计；不同阶段各自从 0 开始。

    本案例的执行路径

    1. Phase.memory() 预留完整阶段包络：常驻状态 + 最终 KV + 最大复用 arena + 融合特征。
    2. Phase.run() 把算子最忙 lane / host 的资源需求组织成串行 Event 链。
    3. engine.simulate() 检查容量和依赖，计启动延迟，分配速率并推进时钟。
    4. 事件完成后记录耗时与瓶颈；全机物理流量单独求和，避免把 rank 耗时累加成延迟。
    T(event) = startup + max(workᵣ / rateᵣ)该等式适用于本案例的串行资源包络。通用引擎支持 max-min 争用；此案例未展开所有物理 rank 的并发事件。

    此案例走独立 pod_dflash / CaseConfig 适配器，复用原生执行器；普通 Config → compile_graph() 的整图链不直接替代 CED / CSA2 和分阶段 batch。

    05 / EVIDENCE & REPRODUCIBILITY

    来源、边界与复现

    当前案例的解释边界

    • 10T 为 64 层 / 7168 hidden 的合成外推，保留 CED、CSA2、mHC、Engram 机制；不是官方 10T checkpoint，也不验证模型质量。
    • 本次使用独立的 5 层 Dense DFlash 草稿器。保留参考配置中的 3 层 DSpark 字段不参与此草稿路径。
    • 净接受 6 为条件输入，不从接受率算法推断，也未额外计入 bonus token。
    • TPOT 是固定上下文一轮耗时除以净接受 token 数，不是长输出平均 ITL、在线服务排队或 P99。
    • 效果图由内置 imagegen 生成，表达部件角色。仿真中容量、带宽、效率与拓扑仍以配置为准。
